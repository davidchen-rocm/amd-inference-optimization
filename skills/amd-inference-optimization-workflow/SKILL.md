# AMD Inference Optimization Workflow

Advance the task through the framework. Let the framework own state and gate decisions; use this skill to supply analysis at stages that require judgment.

## Work from the current state

1. Read the task, current state, permitted next actions, budget, and `agent-context.json`.
2. Read only the evidence referenced by that context. Treat missing or unsupported measurements as unknown, never as zero.
3. Perform only the analysis requested by the current stage.
4. Produce one `AgentDecision` that follows [the decision contract](references/decision-contract.md).
5. Submit the decision to the framework. Accept the next state returned by the framework.

Never edit workflow state, fabricate evidence, skip required stages, or announce `ACCEPT`, `REJECT`, or `INCONCLUSIVE`. The deterministic Gate Engine owns those verdicts.

Treat a missing or incomplete `decision_schema` as a handoff error. Stop and request a rebuilt
context; do not search examples, fixtures, reports, or unrelated repository files to reconstruct the
schema or supplement evidence.

Treat artifact identity as part of the evidence. Use the stored path and SHA-256 together; do not
silently replace an artifact or cite a mutable external path as if it were the captured input.

## Use ROCm evidence through the framework

- Request profiling by setting `requested_profile_level` and identifying the missing evidence.
- Stop escalating when existing evidence is sufficient to distinguish the leading explanations.
- Do not invoke profilers directly. Let the workflow's ROCm MCP adapter create the approved request and preserve the raw response.
- Every executing MCP call needs an immediate, one-use approval bound to the exact tool, argv, cwd,
  preset, timeout, server execution environment, and attempt identifier. A transport failure consumes
  that attempt; request a new approval before retrying.
- Treat Level-2 timing as supporting evidence collected with the framework's canonical short trace:
  one warmed-up tg128 repetition. Do not substitute the wider tg128/tg512 E2E benchmark in a profiler.
  Baseline and every candidate share the same profile argv; runtime-environment differences remain
  explicit. The approval binds both the unchanged E2E protocol hash and the short profile command.
- An inconclusive trace also consumes its approval. Preserve its failure reason and partial artifacts;
  use the new attempt and exact approval generated by the framework for any retry.
- Cite evidence refs from the current task for every measured claim.
- Mark profiler counters that are unsupported, all-zero due to platform limitations, or absent as unavailable.

Use the minimum useful profiling level:

- Level 0: environment, clocks, temperature, ROCm and GPU identity.
- Level 1: repeatable end-to-end benchmark.
- Level 2: kernel timing and dispatch trace.
- Level 3: targeted counters and kernel metadata.
- Level 4: ISA, thread trace, or PC sampling.

Do not request a level merely because it exists in this list. Check live capabilities first. For the
current gfx1201 MVP, kernel timing is usable while kernel metadata, telemetry, and targeted counters
may be unavailable or not integrated. Missing counters leave hardware behavior unknown.

## Analyze before changing code

- Update the execution map incrementally from phase and operator to runtime path, kernel, and hardware behavior. Map the dominant path first.
- Classify the bottleneck with evidence, confidence, competing explanations, and missing evidence.
- Estimate the hotspot's time share and an upper bound on end-to-end benefit before proposing a change.
- Form one primary hypothesis per experiment. State the expected kernel signature, expected end-to-end effect, risks, validation, and stop condition.
- Prefer the smallest patch or runtime configuration that isolates the hypothesis.

When testing a staged chain, preserve each result independently. A deliberately weak first candidate
may be performance-rejected before expensive quality evaluation, then profiled to explain the failure.
The next candidate is a new experiment and must cite the failed experiment; it does not overwrite it.

## Interpret experiments

- Compare only runs with compatible environment fingerprints and benchmark protocols.
- Separate source changes from runtime-configuration changes. Reuse a binary only when its hash is identical and the experiment records that reuse.
- Bind every benchmark and profile to the canonical argv, cwd, device visibility, runtime environment,
  binary hash, model hash, and protocol hash. A profiler run is supporting evidence, not the primary
  throughput measurement.
- Explain failures using measured signatures. Do not rescue a failed hypothesis by changing several unrelated variables in the same experiment.
- For inconclusive evidence, name the exact failed comparability or stability condition and request the earliest stage that must be rerun.
- For rejected experiments, preserve useful negative evidence and propose a new hypothesis only when budget remains.
